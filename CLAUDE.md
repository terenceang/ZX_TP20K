# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Sinclair ZX Spectrum 48K implemented in Verilog for the Sipeed Tang Primer 20K (Gowin GW2A-LV18PG256C8/I7) on its Dock board. The build uses Gowin EDA 1.9.12.04 (`gw_sh`, `programmer_cli`). Video and audio go out over HDMI (720x480p with 48 kHz audio in data islands); the keyboard is a web page over the 1 Mbps (1000000 baud) UART on the Dock's USB-C (BL702). The board's DDR3 is brought up and self-tested (`src/zx_ddr.v`) ready for the cores that use it next (128K banks, storage). The HDMI stack (`src/hdmi/`) and the tv80 core (`src/z80/`) came from the sibling Apple //e project; the board documentation — Dock/SOM schematics, UG290, and the authoritative pin table — is in `Documents/` here.

## Commands

```sh
make rom         # fetch + SHA-256-verify the 48K ROM => roms/zx48.rom + zx48.hex (not in the repo)
make build       # synthesis, place & route, bitstream => build/bitstream/zx_tp20k.fs
make load        # load the bitstream into SRAM (volatile, fast; use for iteration)
make flash       # write the config flash (persistent)
make sim         # all testbenches (iverilog, OSS CAD Suite)
make clean

sim/run.ps1 [-Target tb_name]                    # one testbench
sim/render-screen.ps1                            # build/ram.hex -> build/screen.png
sim/render-screen.ps1 -Rgb build/frame.rgb -Out build/frame.png
scripts/fetch-rom.ps1 [-Url <alt>]               # pinned hash, see roms/README.md
scripts/build.ps1                                # the build itself (gw_sh); the Makefile wraps this
scripts/prog.ps1 [-Flash]                        # Gowin programmer_cli over the Dock's USB-JTAG

cd web; npm install; npm run dev                 # keyboard page (http://localhost:5173)
cd web; npm run build; npm test                  # bundle; protocol/keymap unit tests
```

- **The Makefile has no build logic.** `scripts/build.ps1` generates `build/gowin/build.tcl` from `fpga.yaml`, runs `gw_sh` from the repo root, copies `impl/pnr/zx_tp20k.fs` to `build/bitstream/`, and regenerates `zx_tp20k.gprj` every run so the IDE and the script cannot disagree. It auto-runs `scripts/fetch-rom.ps1` when `roms/zx48.hex` is missing.
- **New source files go in `sources:` in `fpga.yaml` only.** `scripts/sources.ps1` reads that list; `build.ps1` and `sim/run.ps1` (`tb_top`) both consume it.
- **`src/config.vh` is the one build switch.** `ZX_USE_DDR3` decides whether the DDR3 bring-up block (zx_ddr + the encrypted IP + the 398.25 MHz PLL) is compiled in. Nothing in the 48K machine uses the DDR3 yet, and the block is 1364 LUTs (25%), 1296 registers (58%), 8 BSRAMs (17%), 20 pads, one rPLL and the only thin timing margin (`mclk`, +0.26 ns), so it is **out** by default. `scripts/build.ps1` reads the file and picks the matching `.sdc` (`zx.sdc` with it in, `zx_lean.sdc` when out), because the DDR clocks only exist in the former. Set it to 1 for the DDR3 bring-up and the 128K/storage work. `docs/resources.md` has the measured numbers for both builds.
- **`scripts/build.ps1` gates on timing**, not on `gw_sh`'s exit status: it reads `impl/pnr/zx_tp20k_tr_content.html` and fails on any negative setup slack or hold violations. `mclk` (the DDR3 IP's user clock, ~99.6 MHz) is the tight one — its worst paths are inside the encrypted IP, exactly as in the sibling project. `clk_pixel` has ~2x margin.
- **Judge every native tool by its exit code, never by its stderr.** PowerShell turns any stderr from a native command into a terminating error under `$ErrorActionPreference = 'Stop'`; the `gw_sh`, `iverilog` and `vvp` calls each set `Continue` around the call and throw on the exit code. Do not "simplify" them back to bare calls.
- **Run tools from the repo root**: `$readmemh` and `` `include `` paths (`roms/zx48.hex`, `src/hdmi/hdmi_defs.vh`, `src/uart_defs.vh`) are repo-relative.
- **Gowin unrolls `initial` loops and fails above 2000 iterations** (EX3934, "loop count limit"). The 48K of RAM is zero-initialised for simulation inside `// synthesis translate_off/on` — real BSRAM powers up zeroed, and the loop must not reach synthesis.
- **The 48K ROM is copyright and gitignored.** `roms/README.md` has the permission text and the pinned hashes (MD5 `4c42a2f0…`, the canonical image; first bytes `F3 AF 11 FF FF C3 CB 11`).
- `sim/run.ps1` runs every testbench with iverilog and exits non-zero on failure; each bench prints `PASS` or a line starting with `FAIL`. `tb_zx` (the acceptance test) runs with `+fast=2` (27 MHz, the memory path's minimum margin) and proves the authentic power-on screen — see "The power-on screen" in Architecture below.

## Architecture

One clock domain for everything ZX. `clk_gen.v`'s `rPLL` turns the 27 MHz crystal into `clk_tmds` (135 MHz), and `clk_pixel` is derived from `clk_tmds` via a `CLKDIV` (divide-by-5), never tapped off the crystal — the HDMI `OSER10` serializers need a fixed phase relationship between PCLK and FCLK that only a shared hardware divider guarantees; two independently-routed 27 MHz nets drop the display in and out of sync (observed on hardware, sibling project). A second `rPLL` makes `ddr_memory_clk` (398.25 MHz) for the DDR3 IP, whose user clock is `mclk` (~99.6 MHz, `u_ddr/mclk`). The `.sdc` puts `clk`, `{clk_tmds, clk_pixel}`, `ddr_memory_clk` and `mclk` in separate asynchronous groups.

**The CPU is a clock enable, not a clock.** `ce_cpu` is 3.5 MHz — exactly 7/54 of 27 MHz, a fractional accumulator that pulses when `acc + 7 >= 54`. `ce_48k` (the beeper's HDMI audio rate) is 16/9000. Everything that counts real time derives from `VM_PIXEL_HZ` in `src/hdmi/hdmi_defs.vh`; the UART divisor is single-sourced in `src/uart_defs.vh` (27 MHz / 1 Mbps = 27 clocks a bit, exact). Do not write `27_000_000` or a hand-divided count again.

**tv80's read bus must be latched, not live.** tv80 takes a read's byte home one T-state *after* the data phase, through `DI_Reg`, which is `di` sampled at that later edge — by then the address has moved to the next fetch. Feed it the live bus and every register load takes the *next opcode* as its data: `LD A,n` loads the opcode behind it, and the ROM's RAM fill (`LD (HL),n` in a tight loop) writes opcode bytes instead of its operand. The fix is `di_q` in `zx_core.v`: live on the read's T3 (`rd_strobe`), held until the next read. The sibling project's SoftCard (`softcard.v` `di_q`) wraps tv80 with the same latch; the directed test is `sim/tb_tv80.v`.

**Memory timing has two different boundaries.** One 48K RAM serves both the CPU and the video. `zx_video` prefetches the line's 32 bitmap + 32 attribute bytes during the left border (x = 0..63, one read a clock), so the RAM's address mux belongs to the video for `x < 64`; the CPU's enable is masked until `x >= 66` — because the byte a T-state samples at its edge was registered on the clock *before* it, so with the mux switching at 64 the read is valid at 65 and the CPU may sample from 66. Gating both at the same x corrupts one byte per line (the CPU latches the video's byte): that bug reached the editor with a broken pointer and cost a day. No wait states: tv80's address is stable for all 7-8 clocks between enables, so a registered BSRAM read is always final by the T-state that samples it (`ts[2]`). Writes fire once per machine cycle on `ce && ts[2]` (`write` is a machine-cycle constant from the microcode; `mc`/`ts` are one-hot, `mc[0]` = M1, data is sampled at `ts[2]`). `sim/tb_tv80.v` proves LDIR/LDDR, RMW and `INC H` write patterns against this scheme.

**Memory map** (`zx_core.v`): `$0000-$3FFF` ROM (`$readmemh roms/zx48.hex`), `$4000-$FFFF` RAM, screen file at `$4000-$5AFF`. The RAM is clamped (`in_ram ? a-4000 : 0`) so a ROM-addressed read cannot index past the array in sim — the ROM reads `$FFFF` before it ever writes it, and on sim's X that read poisons the CPU (real chips power up random; emulators zero; we zero, in the translate_off block).

**ULA** (`zx_core.v`): decoding is `A0 = 0`. `IN 0xFE` returns `{1,1,1, ~keys}` — bits 4:0 the columns of the row(s) selected by `~A[15:8]`, bit 6 the EAR (idle high). `OUT 0xFE` bits 2:0 border, bit 4 beeper. Interrupts: a 540000-count divider is exactly 50 Hz, `/INT` held 32 T-states like the ULA's. The video frame is 59.94 Hz and deliberately unrelated — the boot never notices, and a mode change can never disturb the interrupt rhythm.

**Video** (`zx_video.v`): the 256x192 ULA picture doubled to 512x384 at (104, 48) of the 720x480 frame, border everywhere else. The screen file is interleaved: `pixel byte = 0x4000 | {0, y[6], y[5:3], y[2:0], 00, x[7:3]}` (scanlines 0x100 apart, character rows 0x20 apart — get these two the right way round; they were swapped once and the picture scrambles vertically), `attribute = 0x5800 | {y[7:3], x[7:3]}`. Attributes: bits 2:0 ink, 5:3 paper, 6 BRIGHT (0xC0 -> 0xFF), 7 FLASH (swapped at ~1.5 Hz, counted from the HDMI frame). Border is always non-bright. Palette channels sit at 0xC0/0xFF; `hdmi_tx` is set `RGB_QUANT(2'b10)` (full range) or a CE-mode sink crushes blacks.

**Keyboard** (`zx_input.v`, `web/`): the host protocol is `0xFE <pos> <down>` (pos = ZX matrix row*5+col, 0..39, row 0 is the CAPS SHIFT row), `0xFF 0x04` all keys up, anything else one ASCII keystroke mapped by the FPGA (CAPS SHIFT for capitals, SYMBOL SHIFT for the red legends — the map is in `zx_input.v`'s `keypos`/`keymap`). Shift keys are ordinary keys (positions 0 and 36), so chords are just two held keys; web keys latch until their up packet, the ASCII fallback holds 40 ms/down 30 ms/up. The page verifies the port with the boot banner (`zx_uart_tx.v` prints `[ ZX Spectrum 20K ]` once after reset).

**DDR3** (`zx_ddr.v`): the sibling project's `aux_ram.v` trimmed to one general client (latch-on-go, ack-pulse, 26-bit word address, byte enables) around the same encrypted Gowin IP in `src/ddr3_memory_interface/`. That is the **1.9.8-generation netlist** — the 1.9.12 core never calibrates on this board (see that directory's README); do not regenerate it. The IP's `.clk` is the **27 MHz crystal**, `.memory_clk` the 398 MHz PLL output — swapping them fails timing by ~300 MHz of negative slack. Calibration, a patterned burst self-test and a masked-write check gate `ready`; `diag` is a static word for bring-up. The 27 MHz client side and the ~100 MHz `mclk` side cross by toggle handshakes; the `.sdc` declares the groups asynchronous.

**HDMI** (`src/hdmi/`): a snapshot of the sibling project's transmitter (both the user's, MIT), proven on this board with picture and audio. Treat it as a snapshot, not a fork. It owns the 720x480p raster (VIC 2) and samples `video_rgb` for its `(pixel_x, pixel_y)`; `zx_video` answers combinationally from its prefetch buffers. `hdmi_tx`'s audio input is the beeper sampled at 48 kHz. `sim/models/gowin_prims.v` has the behavioural `rPLL`/`CLKDIV`/`OSER10`/`TLVDS_OBUF` the benches use (Yosys' cells_sim has only empty shells).

## Hardware notes

- **Build options** (`build.ps1` sets them): `use_sspi_as_gpio 1` (T10 reset, P9), `use_ready_as_gpio 1` (A13), `use_done_as_gpio 1` (C13). HDMI pairs are `TLVDS_OBUF` + `LVDS25 DRIVE=3.5 PULL_MODE=NONE`, both balls of each pair on the `_p` port. DDR3 is `SSTL15`, `BANK_VCCIO=1.5`, balls from Sipeed's DDR3 example.
- **LEDs** (active low): 0 PLL not locked, 1 DDR3 not ready, 2 CPU HALT (breathes in the editor), 3 FLASH phase, 4 keyboard traffic, 5 spare. DDR3 calibration is placement-dependent between builds — check LED 1 before suspecting anything else.
- **Reset** (S0/T10, also `FPGA_RST`): resets the Spectrum only. The DDR3 is not re-initialised (calibration takes ~half a second and its contents survive), as in the sibling project.
- **The board is Dock Rev 3713 with S4 (`RCFG`) on B10 and DIP 1 on C7**; that revision alone does not settle the wiring — see the check-your-board note in `Documents/pinout.md`.
- **The keyboard matrix is not populated**: input is the web page (or a 1 Mbps terminal; any byte that is not `FE`/`FF` is one ASCII keystroke). `zx_input`'s OR-input makes a physical 8x5 matrix on PMODs J12/J14 a drop-in later — the WS2812 ball T9 is the one J14 pin to avoid.
- **The power-on screen is the ROM's, not ours.** The 48K's `NEW` clears the display and then prints `© 1982 Sinclair Research Ltd` through `PO_MSG` (0x1295) *on the bottom line*: `CLS` leaves the lower print line at line 23, column 33 (`0DAA: LD BC,$1721`). It then opens channel K and waits for a key, so the authentic power-on state is a white border, white paper, and that one line of black text in the bottom character row — no report, no cursor. `tb_zx` asserts exactly that (glyphs compared to the ROM's own font bytes at 0x3D00, nothing else inked, all attributes 0x38, the ROM-computed system variables, and the captured HDMI frame). Two values look wrong but are right: `ERR_NR` is **0x00** at the prompt (the RAM test zeroes RAM and only `LINE_SCAN` at 0x1B1E writes 0xFF, when the first line is scanned), and `ERR_SP` is **0xFF50** (the ROM's `0xFF54` minus `EDITOR`'s two pushes at 0x0F2F-0x0F34, under `MAIN_2`'s `CALL EDITOR` return address). `DF_CCL=0x50FC`/`S_POSNL=5/23` is one cell past the message's 28 glyphs; `DF_CC=0x4000`/`S_POSN=33/24` is the main screen's cleared position.
- **Colour bars + 1 kHz tone: hold S1 (T3) or S2 (T2).** `zx_top` muxes `src/colorbar_gen.v` (vendored from the sibling project, unchanged) in front of `hdmi_tx` and swaps the beeper for a 1 kHz square (24 samples per half period at 48 kHz) while either button is held. It is the display-only check: CPU, RAM and the video pipeline are out of the path.
- **The TV effect stage is pipelined, and `zx_video`'s `X0` pays for it.** `zx_tv_fx` (DIP1 colour TV, DIP2 25% scanlines; no mono modes) is three pixel clocks deep, so `zx_core` instantiates `zx_video` with `X0 = 101` instead of 104: the picture lands at x = 104..615 again. Change the pipeline depth and that constant moves with it. The DSP multipliers are used for luma (`Y = 77R + 150G + 29B`); the chroma filter, RGB rebuild and scanline attenuation are shift-adds.
- **Tape: one player, two sources, chosen by `ZX_TAPE_SD` in `src/config.vh`.** `src/tap_player.v` turns a `.TAP` into EAR pulses with the real timings (2168 / 667 / 735 / 855 / 1710 T-states; `tb_tape` measures every half period and the byte order). Default (defined): the **card** — `src/sd/sd_vol.v` + `spi_byte.v` vendored from `apple2e_TP20K` (hardware-proven SD/FAT32), patched only where a `.TAP` replaces a floppy image (`ZX tape:` markers). Its config file is **`ZXCONFIG.TXT`**, read from the card root, with `TAPE=TAPE.TAP` (or the inherited `S6D1=` form); `src/zx_tape_sd.v` joins its `f_up_*` byte stream to the player through a FIFO, and the SPI clock stalls when the FIFO is full, so the tape is pulled at cassette speed. The deck is **on hold until the ROM enters LD-BYTES (0x0556)** — `zx_core`'s `tape_load` pulse — so the leader starts exactly when `LOAD ""` runs; **DIP5** (`sw_tape_auto`) makes it roll from reset instead. Undefined: the **web** deck (`src/zx_tape_web.v`) — `0xFD <byte>` in and a `0x06` credit byte back on the keyboard UART, driven by the page's *Load tape* button (`web/src/tape.js`), which also types `LOAD ""`. LED5 is on while either plays.
- - - - **Working on the boot**: `tb_zx` dumps the whole 48K (`build/ram.hex`), prints the ROM's system variables and writes one 720x480 RGB frame of the real video output (`build/frame.rgb`); decode the screen with `sim\render-screen.ps1` (or `-Rgb build\frame.rgb -Out build\frame.png` for the HDMI picture). `tb_dbg` samples the PC; `tb_ts` traces T-states, read strobes and writes in a window; `+trace=1` on `tb_zx` prints every system-variable write with the PC that made it.
- **Simulating the boot** takes patience: the ROM's power-on RAM test fills `$02` down from `$FFFF` (32 T-states a byte, ~450 ms), walks the whole 48K, and runs a second pass — several seconds of machine time. `+fast=2` (27 MHz: T1->T3 is then exactly the two clocks a registered read needs, the minimum-margin stress) boots by ~240 ms of machine time and takes a few minutes of simulator time; `+fast=1` (13.5 MHz) is ~2x longer, and `+ms=300` is enough for `+fast=2`. `+noint=1` forces the interrupt idle to split CPU/path problems from interrupt problems.
- **The web page talks over Web Serial directly** (Chrome/Edge, secure context, user gesture — hence the Connect button). The port is confirmed by waiting for the boot banner; a board that has been up a while has already printed it, so the page connects *unverified* and says so rather than closing. Baud is 1 000 000 8N1 — a terminal at 115200 produces garbage packets, which the FPGA drops.
